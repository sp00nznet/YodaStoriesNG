# Capturing screenshots

Every image in this repository is generated by a script from a real run of the game. None of
them are hand-taken, and none of them are stale, because regenerating the lot is one
command.

```powershell
pwsh tools/capture-shots.ps1
```

Roughly two minutes. Windows will open, play themselves, and close.

---

## Why it works this way

Hand-taken screenshots rot. The HUD moves, a colour changes, a feature is added, and the
README quietly starts advertising a version of the software that no longer exists. Worse,
nobody notices, because looking at a screenshot does not tell you when it was taken.

Generated shots have the opposite failure mode: if the game changes, the next capture shows
the change. If the game breaks, the capture fails loudly. It doubles as a smoke test - a run
that produces a gameplay shot with items in the inventory is a run where the bot walked,
fought and traded to get them.

---

## How it works

Three stages.

### 1. The sink

`src/YodaStoriesNG.Engine/Dev/Capture.cs`. Dormant unless the `YSNG_CAPTURE_DIR`
environment variable is set, so it costs a released build one string comparison per frame.

Every SDL window in the game calls `Capture.Flush(renderer, tag)` immediately before its
`RenderPresent`, tagged with its own name - `"game"`, `"map"`, `"assets"`, `"score"` and so
on. The harness calls `Capture.Request(tag, name)`; the next frame that window draws, its
backbuffer is written out as a BMP.

The hook sits **before** `RenderPresent` because reading pixels after presenting is
undefined. That is also why each window flushes itself rather than the game loop doing it
centrally - each one owns its own renderer and its own present.

The BMP writer is 54 bytes of header and a `memcpy`. SDL hands back `ARGB8888`, which on a
little-endian machine is `B,G,R,A` in memory - exactly BMP's byte order - so no conversion
is needed and no image library is involved. ffmpeg turns the BMPs into PNGs and GIFs later.

### 2. The timeline

`src/YodaStoriesNG.Engine/Dev/CaptureScript.cs`. A list of `(at seconds, do this)` steps,
built once and stepped by the game loop. It attaches to `GameEngine` as a `partial` class,
because every screen worth capturing is reached through private engine state and inventing a
scripting seam for it would be more machinery than the job needs.

The sequence, about 45 seconds:

| Time | What happens |
|---|---|
| 0.4 - 7.2 s | 90 frames of the title screen, covering one full pass of the X-Wing flyby. Becomes `docs/hero.gif`; frame 45 becomes `title-screen.png`. |
| 7.6 s | Dismiss the title, start a new game. |
| 8.1 s | Enable the mission bot and let it play for 17 seconds. |
| 25 s | Park the bot and clear its toast messages, so the shot shows the game rather than the harness. |
| 26 s | The gameplay shot. |
| 27 s | Jump to the most colour-cycled zone in the game, then 24 frames at 75 ms. Becomes `palette-animation.gif`. |
| 30 s | Move to the zone with the most readable scripted dialogue. |
| 30 - 38 s | Open, capture and close each tool window: map, script editor, asset viewer, save editor. |
| 38 s | Trigger an R2-D2 hint and capture the dialogue over the live game. |
| 40 s | Stage a finished run and capture the score screen. |
| 42 s | Quit. |

Two of those steps pick their subject rather than hard-coding it, so they stay right as the
data changes:

- **`FindMostAnimatedZone`** scores every tile by how many of its 1,024 pixels use a
  colour-cycled palette index, then scores every zone by the tiles it uses. The winner is
  the zone with the most water, lava and fire on screen - the one where the palette
  animation is actually visible. On Yoda Stories it reliably picks a Dagobah swamp.
- **`FindRichestScriptZone`** scores zones by how much *readable* dialogue their scripts
  carry, counting only text that is more than 90% letters and spaces. Garbled runs of
  section tags cannot win, so a misaligned parser produces a low score rather than a
  confident screenshot of nonsense.

### 3. The conversion

`tools/capture-shots.ps1` builds Release, runs the engine twice - once on `YODESK.DTA`, once
on `DESKTOP.DAW` - and converts the frames with ffmpeg.

GIFs go through ffmpeg's two-pass palette route: `palettegen=stats_mode=full` over the whole
sequence, then `paletteuse=dither=none`. The single-pass default quantises each frame
independently and bands these already-8-bit images badly; dithering adds noise to art that
has none. Scaling uses `flags=neighbor` for the same reason - this is pixel art and it
should stay sharp.

## Output

| File | Source |
|---|---|
| `docs/hero.gif` | Title screen, X-Wing flyby, 90 frames at 640px |
| `docs/shots/title-screen.png` | Frame 45 of the same |
| `docs/shots/gameplay-yoda.png` | Bot-played Yoda Stories |
| `docs/shots/gameplay-indy.png` | Bot-played Indiana Jones |
| `docs/shots/palette-animation.gif` | 24 frames, cropped to the play area |
| `docs/shots/world-map.png` | Map Viewer |
| `docs/shots/script-editor.png` | Script Editor |
| `docs/shots/asset-viewer.png` | Asset Viewer |
| `docs/shots/save-editor.png` | Save Game Editor |
| `docs/shots/score-screen.png` | Force Factor screen |
| `docs/shots/r2d2-help.png` | R2-D2 hint dialogue |

**Gameplay shots differ every run**, because every run generates a different world. That is
deliberate: they should look like the game, not like one blessed save file. If a shot lands
somewhere dull, run it again.

## Options

```powershell
# Data in non-default locations
pwsh tools/capture-shots.ps1 -YodaData "D:/Games/Yoda" -IndyData "D:/Games/Indy"

# Keep the intermediate BMPs, e.g. to hand-pick a different frame for a still
pwsh tools/capture-shots.ps1 -KeepFrames
```

Without `-KeepFrames` the frames are deleted; with it they stay in
`%TEMP%/ysng-capture/`.

Missing `desktop.daw` is a warning, not an error - you get every shot except
`gameplay-indy.png`.

## Adding a shot

1. **Give the window a tag.** If it is a new window, add
   `Dev.Capture.Flush(_renderer, "your-tag");` on the line above its `SDL.RenderPresent`.
   Existing windows already have one.
2. **Add a step to the timeline** in `CaptureScript.cs`: open the thing, wait a beat,
   `Dev.Capture.Request("your-tag", $"{game}-your-shot")`, close it.
3. **Add a conversion line** to `tools/capture-shots.ps1`:
   `Convert-Still 'yoda-your-shot' 'your-shot'`.
4. Run it and look at the result.

Frame timing lives in the constants at the top of `CaptureScript.cs` and is mirrored by
`$fps` in the script. Change one, change the other.

---

## Running it by hand

If you want the frames without the conversion:

```powershell
$env:YSNG_CAPTURE_DIR = "C:\temp\shots"
dotnet src\YodaStoriesNG.Engine\bin\Release\net8.0\YodaStoriesNG.Engine.dll Yoda
Remove-Item Env:\YSNG_CAPTURE_DIR
```

The engine quits itself when the timeline ends. Do not touch the windows while it runs - the
harness is on a clock, not waiting on you.
